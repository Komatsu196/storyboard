# プロダクト決定事項ログ

絵コンテ管理アプリの方向性に関する決定事項を、ヒアリングの進行順に記録する。

- 番号は決定順（D-001, D-002, ...）。
- 決定が覆った場合は元の項目の「状態」を「取り消し（→D-xxx）」に、一部だけ変わった場合は「一部修正（→D-xxx）」に変え、新しい番号で追記する（履歴は消さない）。
- 各項目は「決定 / 背景 / 含意（この決定から導かれること）」で書く。

## D-001: 最初のターゲットユーザーは「自分自身（個人制作）」

- **決定**: 最初のターゲットユーザーは開発者本人。個人制作の実写映像の絵コンテを管理する用途に絞る。
- **背景**: ヒアリング Q1「このアプリは、まず誰のために作りますか？」への回答。選択肢は「自分自身 / 自分＋少人数チーム / 制作会社・スタジオ / 広く一般のクリエイター」。
- **含意**:
  - MVP ではマルチユーザー・共有・権限・コラボレーション機能を持たない。
  - 認証は「自分だけが使える」ことを担保できれば十分（方式は技術決定で別途決める）。
  - 機能の優先順位は「自分のワークフローに刺さるか」で判断する。一般化・汎用化は後回し。

## D-002: 扱う絵コンテのドメインは「実写映像・ショートフィルム・MV」

- **決定**: 撮影前のショット設計（ショットリスト）としての絵コンテを対象にする。アニメ絵コンテ・マンガのネーム・動画企画の構成表は対象外。
- **背景**: ヒアリング Q2「扱いたい絵コンテは主にどの分野のものか」への回答。
- **含意**:
  - 基本単位は「カット（ショット）」。カットには画のほかに、カメラに関する情報（サイズ・動きなど。アングル・レンズは D-007 で除外）と芝居・セリフ・尺が付随する。
  - 撮影当日にショットリストとして参照される利用シーンを考慮する。
  - アニメ用の「秒＋コマ」表記やマンガのページ単位の構造は考えなくてよい。

## D-003: 「描く」はアプリの外（紙・iPad）で行う前提に立つ

> **状態: 取り消し（→D-011）** — ヒアリング Q9 で「スケッチがメインであってほしい。1ツールで完結する手軽さが大事」と方向が示されたため、この前提を撤回した。紙・iPad で描いた画像の取り込みは「補助的な入口」として残る。

- **決定**: 絵そのものは紙・ノートへの手描き、または iPad などのタブレットで描いて画像として保存する現状の手段を継続する前提とする。アプリの主戦場は「描いたあと」の管理にある。
- **背景**: ヒアリング Q3「今は絵コンテをどう作って、どこに保管しているか」への回答が「紙・ノートに手描き」「iPad・タブレットで描いて画像保存」の併用だったため。
- **含意**:
  - 画像（紙を撮った写真、タブレットからの書き出し）の取り込みがアプリの入口になる。
  - 描画キャンバス機能を MVP に含めるかどうかは別途判断する（D-005 以降で決定）。

## D-004: 中心価値は「1カット＝画＋撮影情報」をひとつの単位で持つこと

- **決定**: このアプリが最初に解く課題は「画と情報を一緒に持てない」こと。1カットを「画像＋構造化された撮影情報」としてひとまとまりで保持・閲覧・編集できることを MVP の中心に置く。
- **背景**: ヒアリング Q4「今のやり方で一番困っているのは何か」への回答。選択肢は「散らばって見つけられない / 構成（順番）をいじれない / 画と情報を一緒に持てない / 現場で使えない・出力できない」で、「画と情報を一緒に持てない」が最も痛いと判断された。
- **含意**:
  - データモデルの中心は「カット」エンティティで、画像とメタデータを1対1で結びつける。
  - 「探せる」「並べ替えられる」「出力できる」は中心価値を支える周辺機能として、優先度を別途決める。
  - 撮影情報として何を持つか（項目の定義）は次の決定事項で確定する。

## D-005: 描画は「簡易スケッチ・書き込み」まで。本格的な描画ツールは作らない

> **状態: 一部修正（→D-011）** — 「本格的な描画ツールは作らない」「ラフな棒人間程度で良い」という線引きは維持する。ただし含意にある「画像取り込みが主、簡易スケッチは従」「MVP に含めるかは別途判断」は D-011 で覆り、**簡易スケッチが主で MVP の中心**になった。

- **決定**: アプリ内の描画機能は「取り込んだ画像への矢印・メモの書き込み」「ラフな棒人間程度のスケッチ」に限定する。レイヤー・ブラシ・カラーパレットなどを備えた本格的な描画ツールは作らない。
- **背景**: ヒアリング Q5「アプリ内で描く機能は必要か」への回答。選択肢は「不要（画像取り込みのみ）/ MVPでは不要・将来は欲しい / 簡易なスケッチ・書き込みは欲しい / アプリ内で描きたい」。
- **含意**:
  - 画像取り込み（D-003）が主、簡易スケッチは従。「画像なし・スケッチのみ」のカットも存在しうる。
  - 必要なのはペン・消しゴム・数色・取り消し程度のシンプルなキャンバス。iPad のペン入力で使えることが望ましい（プラットフォーム決定と併せて確認する）。
  - 簡易スケッチを MVP に含めるかどうかは、優先順位づけの決定（後述）で確定する。

## D-006: 設計原則「できる限りシンプルに」— 迷ったら足さない

- **決定**: プロダクト全体の設計原則として「できる限りシンプル」を掲げる。項目・機能・画面のいずれも、追加を迷ったら足さない。必要になったときに足す。
- **背景**: ヒアリング Q6（カットの項目案）に対して「アングル・レンズ・INT/EXT・DAY/NIGHT は不要。できる限りシンプルで良い」との回答。項目の取捨選択だけでなく、プロダクト全体の姿勢として明文化した。
- **含意**:
  - 「あると便利かも」は採用理由にならない。「自分が実際に毎回書く／使う」ものだけを入れる。
  - 入力必須の項目は最小限にし、空のまま保存できるようにする（入力の摩擦を減らす）。
  - 以降の決定（MVP スコープ・画面設計・技術選定）はすべてこの原則に照らして判断する。

## D-007: 構造は 作品 → シーン → カット。カットの項目は8つに確定

- **決定**: データ構造は「作品（Project）→ シーン（Scene）→ カット（Shot）」の3階層。各階層の項目は次の通り。

  **作品**
  | 項目 | 形式 |
  | --- | --- |
  | タイトル | テキスト |
  | アスペクト比 | 選択式（16:9 / 9:16 / 4:3 / 2.39:1、既定 16:9）※D-013 で追加 |

  **シーン**
  | 項目 | 形式 |
  | --- | --- |
  | シーン番号 | 自動採番＋手動調整 |
  | タイトル | テキスト |

  **カット**
  | 項目 | 入力形式 | 例 | 必須 |
  | --- | --- | --- | --- |
  | カット番号 | 自動採番＋手動調整（枝番可） | 1, 2, 2A | 必須 |
  | 画 | 簡易スケッチ（画像取り込みは Later、D-013） | — | 空も許容 |
  | ショットサイズ | 選択式 | LS / FS / MS / BS / CU / ECU | 空も許容 |
  | カメラの動き | 選択式＋自由入力 | Fix / Pan / Tilt / Dolly / Handheld / Gimbal | 空も許容 |
  | 内容（芝居・アクション） | 自由テキスト | 「Aが振り返る」 | 空も許容 |
  | セリフ・音 | 自由テキスト | 「A：おはよう」「SE：ドアの音」 | 空も許容 |
  | 尺 | 秒（数値） | 3 | 空も許容 |
  | 備考 | 自由テキスト | 「三脚必要」 | 空も許容 |

- **背景**: ヒアリング Q6 でたたき台（10項目＋シーンに INT/EXT・DAY/NIGHT・場所）を提示し、「アングル」「レンズ」「INT/EXT・DAY/NIGHT」を不要と回答。D-006 の原則に沿ってシーンの「場所」も外し、番号とタイトルのみに絞った。
- **含意**:
  - DB スキーマはこの3エンティティが土台になる。項目の追加は D-006 に照らして慎重に行う。
  - 「必須」はカット番号のみ。カットは番号さえあれば作成でき、画も情報もあとから埋められる。
  - ショットサイズ・カメラの動きの選択肢は固定リストで始める（ユーザー定義は現時点では作らない）。

## D-008: 使う端末は PC とスマホ。PC で組み、スマホで書き足し・現場で見返す

- **決定**: 利用場面は次の3つ。iPad は「描く道具」であり、アプリ自体の主要な利用端末とはしない。
  1. **PC ブラウザで構成を組む** — 机に座って、カットを並べ、情報を入力する。広い画面での一覧性を重視。
  2. **スマホで空き時間に書き込む** — 思いついた内容・セリフ・備考などを、移動中などの空き時間にその場で入力する。
  3. **スマホで現場で見返す** — 撮影当日にショットリストとして確認する。片手・縦画面での閲覧が中心。
- **背景**: ヒアリング Q7「主にどの端末・場面で使うか」への回答。「PCブラウザで構成を組む」「スマホで現場で見返す」に加え、「スマホでも書き込みできるようにしたい。空き時間に書き込める感じ」との補足があった。「iPadで描きながら使う」「紙に印刷して現場に持っていく」は選ばれなかった。
- **含意**:
  - Web アプリとしてレスポンシブに作る。PC は一覧（表・グリッド）中心、スマホは1カットずつの縦並び中心、という2つのレイアウトを持つ。
  - スマホは「閲覧専用」ではなく**編集もできる**必要がある。スマホでの入力フォームの使いやすさが重要。
  - 簡易スケッチ（D-005）をスマホの指操作で行うかは、MVP スコープの決定時に判断する。→ D-012 で「スマホの指で描く」と確定。
  - 撮影現場での利用があるため、通信環境が悪い場面での挙動（オフライン対応の要否）を別途決める（D-010 以降）。

## D-009: PDF 出力・印刷は MVP では作らない

- **決定**: PDF 書き出し・印刷用レイアウトは MVP に含めない。現場での参照はスマホ画面で行う（D-008）。
- **背景**: ヒアリング Q7 で「紙に印刷して現場に持っていく」が選ばれなかったため、D-006（迷ったら足さない）に従って除外した。
- **含意**:
  - 必要になった時点で追加を検討する。データ構造（D-007）は出力形式に依存しないので、後から足せる。

## D-010: オフライン対応はしない（常時オンライン前提）

- **決定**: 撮影現場を含め、通信できる環境で使う前提に立つ。オフライン閲覧・オフライン編集のいずれも作らない。電波の無い現場では、事前にスクリーンショットを撮るなどの運用で対応する。
- **背景**: ヒアリング Q8「撮影現場で電波が無いとき、アプリはどう振る舞えばよいか」への回答。選択肢は「不要 / 見るだけはオフラインで / オフラインでも編集したい」。D-006 の原則に沿って「不要」を選択。
- **含意**:
  - 端末内へのデータ保持や同期・競合解決の仕組みは不要。サーバー側に唯一の正（single source of truth）を置く素直な構成にできる。
  - Service Worker やローカル DB を前提とした設計はしない。
  - スマホでの閲覧を軽くするため、画像はサムネイル等で軽量に配信することは別途考慮する（技術決定）。

## D-011: 「描く」がメイン。1ツールで完結する手軽さを中心価値に据える

- **決定**: このアプリは「ラフな絵コンテを描いて、その場で撮影情報を書き込める、1ツールで完結する手軽な絵コンテアプリ」である。簡易スケッチは MVP の中心機能であり、周辺機能ではない。
  - 描画は D-005 の線引きどおり「ラフな棒人間・矢印・メモ」で十分とする。**ラフで良いからこそ速く、1ツールで完結できる**ことを売りにする。
  - 紙・iPad で描いた画像の取り込み（旧 D-003）は補助的な入口として残す。
  - D-004「1カット＝画＋撮影情報」は維持する。画は「アプリ内で描いたスケッチ」が第一、「取り込んだ画像」が第二。
- **背景**: MVP スコープ案（簡易スケッチを「MVP の次」に置く案）に対して、「スケッチは MVP に含めたい。どちらかというとそれがメインであってほしい。1ツールで完結する手軽さが大事」との回答。
- **含意**:
  - MVP の成功基準は「描いて・書いて・見返す」が1ツールで回ること。スケッチ機能の使い心地が MVP の成否を決める。
  - キャンバスは「ペン・消しゴム・取り消し・数色」程度の最小構成で、開いてすぐ描ける速さを最優先する。
  - どの端末で描くか（スマホの指 / iPad のペン / PC のマウス）で必要な入力対応が変わるため、次の決定で確定する。→ D-012 で「スマホの指・PC のペンタブ」と確定（D-008 の端末構成は維持）。
  - 実写用の画面フレーム（アスペクト比）をキャンバスに持たせる必要がある。既定値と切り替えの要否は MVP スコープの再提案で決める。→ D-013 で「作品ごとに選択、既定 16:9」と確定。

## D-012: スケッチは「スマホの指」と「PC のペンタブレット」で描く

- **決定**: アプリ内スケッチの入力手段は「スマホを指で」「PC をペンタブレットで」の2つ。iPad + Apple Pencil、PC のマウスは主要な入力手段としない（動いても構わないが、そのための作り込みはしない）。
- **背景**: ヒアリング Q10「アプリ内でスケッチを描くのは主にどの端末・入力か」への回答。選択肢は「スマホを指で / iPad を Apple Pencil で / PC をマウス・トラックパッドで / PC をペンタブレットで」。
- **含意**:
  - キャンバスは指（touch）とペン（pen）の両方を同じ仕組み（Pointer Events）で扱う。ペンの筆圧が取れれば線の太さに反映してもよいが、取れなくても成立する作りにする。
  - スマホの指描き前提: 描画中にページがスクロールしない、ツールボタンは大きく少なく、太めの線でも読めるラフさを許容する。
  - Apple Pencil 特有の対応（パームリジェクション等）や、マウス向けの補助（直線・図形ツール等）は作らない。
  - D-008 の端末構成（PC とスマホ）は変わらない。PC 側は「構成を組む」に加えて「ペンタブで描く」場面が加わる。

## D-013: MVP スコープの確定（スケッチ中核・7項目、画像取り込みは Later）

- **決定**:

  **成功基準** — 実際の1本（ショートフィルム or MV）で「描く → 情報を書く → 見返す」が全部このアプリの中で回り、撮影を終えられる。紙・iPad・他ツールを併用せずに1本使い切れたら MVP 成功。

  **MVP に入れるもの（優先順）**
  1. **スケッチキャンバス（中核）**
     - ツール: ペン（太さ2〜3段階）・消しゴム・取り消し/やり直し・全消し
     - 色: **黒＋赤の2色**（赤は矢印・カメラの動きの書き込み用）
     - **フレーム枠**を表示する。アスペクト比は**作品ごとに選択**（16:9 / 9:16 / 4:3 / 2.39:1、既定 16:9）
     - 描いたスケッチは**あとから開いて追記・消去できる**（描き直しのたびに全消しにならない）
     - スマホの指・PC のペンタブで描ける。描画中にページがスクロールしない（D-012）
  2. **カット追加 → 即キャンバス**の動線（特にスマホ。「＋カット」ですぐ描き始められる）
  3. カット情報（D-007 の8項目）の入力・編集。キャンバスと同じ画面で行う
  4. 作品・シーン・カットの作成・並べ替え・削除（自動採番、番号の手動調整）
  5. PC 向け一覧: **スケッチのサムネイルを並べたグリッド**（絵コンテ用紙のように俯瞰できる）
  6. スマホ向け閲覧: 1カットずつ縦にスクロール（現場用、D-008）
  7. 自分だけが使えるログイン（D-001。方式は技術決定で決める）

  **MVP の次（Later）**
  - 画像アップロード（紙・iPad の絵の取り込み。1枚ずつ）— **MVP から外した**
  - 画像の一括取り込み、カットの複製・シーン間移動、尺の合計表示、検索・タグ、色の追加、スケッチへのテキスト入力

  **やらないこと（決定済み）**
  - 本格描画（レイヤー・ブラシ）D-005、PDF/印刷 D-009、共有・複数ユーザー D-001、オフライン D-010、iPad/マウス向けの作り込み D-012

- **背景**: D-011・D-012 を踏まえて再提案した MVP 案に対し、「フレーム枠は選べる設計」「色（黒＋赤）は足りる」「画像アップロードは Later でよい」との回答で確定。
- **含意**:

  - 作品エンティティに「アスペクト比」項目が加わる（D-007 の作品項目に追加: タイトル / アスペクト比）。
  - MVP の完成判定は機能の有無ではなく「自分の1本で使い切れたか」で行う。

## D-014: フロントは Vite + React + TanStack Router の SPA。DB・ストレージは提案制

- **決定**:
  - フロントエンドは **Vite + React + TanStack Router** の SPA として作る。**TanStack Start（SSR・サーバー関数）は使わない**。
  - DB・ストレージは技術設計フェーズで提案して決める。Cloudflare D1 などが候補。
  - ホスティングは Cloudflare を前提とする（D1 が候補に挙がったことからの推定。技術設計時に確認する）。
- **背景**: ヒアリング Q11「技術スタックについて、すでに決まっている（変えたくない）のはどこまでか」への回答。「TanStack Start まではいかずに Vite / React / TanStack Router の想定。DB・ストレージは基本的に提案してもらいたい。D1 など」。
- **含意**:
  - 現在の `apps/web` スキャフォールドは TanStack Start ベース（`@tanstack/react-start`、`server-entry`、Drizzle + MySQL）なので、**技術設計で構成を組み直す**必要がある。Tailwind / Biome / Drizzle はそのまま使える可能性が高い。
  - SPA から D1 / R2 に直接は触れないため、**Cloudflare Workers 上の軽量 API**（例: Hono）が必要になる。SPA と API を同じ Worker から配信する構成が候補。
  - スケッチの再編集要件（D-013）から、ストローク情報（JSON）とサムネイル画像（PNG）の2種類の保存先を設計する。
  - 個人利用のため、**無料枠に収まる構成**を前提に選定する（費用制約。異論があれば別途決定を追記する）。

## D-015: MVP の目標日は 2026-10-14（1ヶ月以内に自分の1本で試す）

- **決定**: MVP（D-013）を 2026-10-14 までに「自分の1本で使い始められる状態」にする。その頃に描きたい企画があり、それを MVP の実戦テスト（成功基準の判定）に使う。
- **背景**: ヒアリング Q12「MVP をいつまでに使える状態にしたいか」への回答。選択肢は「期限なし・じっくり / 最速で叩き台 / 1ヶ月以内に自分の1本で試したい / 具体的な撮影予定がある」。
- **含意**:
  - 1ヶ月という期間は「作り込んでから使う」には短く、「叩き台を触りながら決める」には長い。**まずスケッチキャンバス（D-013 の 1〜3）を最初の1〜2週間で触れる状態にし、残りの期間で一覧・並べ替え・ログインを足す**進め方が合う。
  - スコープを足す判断は D-006（迷ったら足さない）に加えて「10/14 に間に合うか」でも縛る。
  - 実戦テストで出た改善点は、MVP 後の Later（D-013）の優先順位づけに使う。
